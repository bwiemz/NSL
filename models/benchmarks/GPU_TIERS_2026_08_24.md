# Single-GPU certification tiers — measurement record (2026-08-24)

Roadmap item 14. One front door, three depths:

```text
scripts/gpu-tier.sh smoke | certify | endurance
```

Hardware: NVIDIA RTX PRO 4500 Blackwell 32 GB (sm_120), driver 610.57.04,
CUDA 13.x toolkit. `CARGO_TARGET_DIR` on real disk (never tmpfs), `TMPDIR`
under it. Every number below was produced through the tier front-end itself —
the measurement doubles as the wiring's first end-to-end execution.

validation (`PROD1B_VALIDATION_2026_08_19.md`). Re-running a GPU-day
workload to re-prove an unchanged code path would be measurement theater.

## The concurrency guard is load-bearing, not decorative

Every tier (and all nine campaign drivers under `models/benchmarks/`) starts
through `scripts/gpu-guard.sh` / `gpu_guard.py`:

- **flock** on one machine-wide path excludes concurrent *guarded* runs;
- the **compute-app check** refuses when any process holds > 256 MiB of VRAM
  (kwin_wayland idles at ~125 MiB as a compute app, so the threshold clears
  a desktop but catches any real training remnant by orders of magnitude);
- refusal is a **hard exit that names the offender** — never a warning. The
  2026-08-19 incident is why: a sweep that printed `WARNING: GPU still at
  24459 MiB` and proceeded lost three measurements and two whole LR-sweep
  arms, and the failures read as compute bugs (`nsl_tensor_matmul` abort at
  step 0) rather than as a busy device;
- workloads run under `setsid` with signals forwarded to the **process
  group**, so killing a tier cannot orphan an `nsl run` child that keeps
  the VRAM (the incident's mechanism).

GPU-free proof: `crates/nsl-cli/tests/gpu_tier_gate.rs` (10 tests, PATH-shimmed
`nvidia-smi`) — refusals fire and name the offender, sub-threshold desktop
state does NOT refuse, the flock excludes a second run, the workload leads its
own process group, both cert entry points refuse before any work, and
list/dry-run operations stay unguarded (a guard that fires for operations that
never touch the device teaches operators to bypass it).

## What the first tier-driven lane run also proved

- The guard-wrapped re-exec chain (`gpu-tier.sh certify` → `gpu-guard.sh run`
  → `gpu-cert.sh --run`) preserves tier selection via `NSL_CERT_TIER` and
  reaches preflight on the real device.
- The per-run inventory hoist (one full-tree scan instead of one per target)
  removed ~5 minutes of pure re-scanning from every lane run.
- Four gates existed that no lane had ever run: the two M46 determinism
  gates, the dropout parity gate, and the SR-BF16 parameter-surface gate had
  landed after the last manifest regen — one of them (`requires GPU` reason)
  additionally fell through every classifier ALLOW pattern and would never
  have run under ANY manifest state. First-execution results are in the
  certify section below.

## Certify tier — full lane result

**63 m 32 s wall** (128% CPU, warm target dir) for 397 gates across 124
targets — the first measured wall clock the lane has ever had (the nightly
cron has never been picked up by a runner; every scheduled run since it was
added queued for 24 h and auto-cancelled). The 30–90 min tier envelope is
therefore real, measured, with headroom.

Result: **391 PASS / 2 FAIL / 4 NOTFOUND.** The 4 NOTFOUND are the known-red
NCCL lib gates (no `nccl` feature in CERT_FEATURES — documented). Both FAILs
were triaged to conclusion:

- `weight_decay_groups_gate::fused_multi_launch_partitions_on_weight_decay_gpu`
  — the GATE was the bug: its hand-rolled `nsl_binary()` probe only knew
  repo-local `target/`, ignoring `CARGO_TARGET_DIR`, so it panicked "build it
  first" on exactly the redirected-target configuration the lane and CI
  mandate. Fixed (probe honours `$CARGO_TARGET_DIR` first; same latent copy
  fixed in `rope_cache_gate.rs`); passes solo in 3 s post-fix. It had only
  ever been green on checkouts with a populated local `target/`.
- `transient_arena_gpu_gate::arena_parity_script_passes` — 224 s of
  `gpu-guard.sh: unknown subcommand: held` ending in fork-table exhaustion:
  this session edited `arena-parity.sh` to call a guard subcommand that was
  not on disk yet WHILE the lane was executing, and the wrapper's
  refusal-path re-exec'd itself unboundedly. Self-inflicted mid-lane edit,
  not a property of the tree; the loop is structurally impossible with the
  committed guard (`held` exists, and the token check terminates the
  recursion). Lesson banked: never edit a script a running lane executes —
  "not currently running" is not "not reachable by the run".

  The gate's UNDERLYING status, measured post-fix with a release nsl:
  the script runs both full arms (7 m 46 s) and the loss-stream parity
  half now PASSES — the fast "loss streams differ" failure still
  reproducible on pre-#524 main is gone. What remains is the filed
  pre-existing red: the cuda-graph arm is vacuous, `captured=0 taints=2`
  on both arms (bf16-storage casts + batched-sgemm taint capture keep the
  regions eager). Entered in `ci/gpu-cert-known-red.txt` with that
  rationale; deleting the row when capture works re-arms the gate.

First-ever execution of the gates the stale manifest had orphaned:

- both M46 determinism gates (`deterministic_flash_backward_gate`) — **PASS**,
  ~98 s batched;
- `srbf16_parameter_surface_is_accounted_as_weights_gpu` (the gate the
  classifier hole had silently excluded from every possible lane) — **PASS**,
  ~16 s.

Slowest gates, for future budget work: `pretrain_loss_decrease_gpu_e2e`
523 s (inside its 1800 s long-arm row), `matmul_cublas_tf32_default_sanity`
352 s, `matmul_cublas_pedantic_equivalence_llama` 351 s. No new long-arm
rows needed.
