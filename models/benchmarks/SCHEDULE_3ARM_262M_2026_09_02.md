# The schedule was the cause: three matched continuations from 262M tokens

**2026-09-02.** The 1B gate established that the intermediate run peaked at
262M tokens and degraded from there at 5σ, under a cosine sized for the full
22.6B epoch that leaves a 1B run at 99.67% of peak LR throughout. This
campaign asks whether SCHEDULE SHAPE is the cause, from the best checkpoint in
that trajectory rather than from initialization.

Three arms, 32,000 micro (131.072M tokens) each, branched from the SAME
checkpoint on the SAME subsequent examples, scored every 8,000 micro
(32.768M tokens). 17 GPU-hours total.

| arm | schedule | lr at branch | lr at end |
|---|---|---|---|
| **A** | the production schedule, unchanged | 1.499734e-5 | 1.499342e-5 |
| **B** | same LR at the branch, cosine sized to the arm | 1.499734e-5 | 4.500000e-6 |
| **C** | 0.5× B pointwise (base and min_lr both halved) | 7.498670e-6 | 2.250000e-6 |

## Result

| tokens | A stack | A web | B stack | B web | C stack | C web |
|---|---|---|---|---|---|---|
| 262,144,000 (branch) | 3.8724 | 5.8341 | 3.8724 | 5.8341 | 3.8724 | 5.8341 |
| 294,912,000 | 4.0541 | 5.9449 | 3.8951 | 5.7940 | 3.7647 | 5.7577 |
| 327,680,000 | 4.2702 | 6.0306 | 3.9029 | 5.7906 | 3.7903 | 5.7609 |
| 360,448,000 | 4.3287 | 6.1449 | 3.8417 | 5.7757 | 3.7980 | 5.7609 |
| 393,216,000 | **4.4114** | **6.1294** | **3.8259** | **5.7625** | **3.7975** | **5.7546** |

Least-squares slopes, nats per 100k micro (+ = worse), over 5 uniformly-spaced
points:

| arm | STACK | WEB | endpoint vs branch |
|---|---|---|---|
| A | **+1.691 ± 0.240 (7.1σ)** | **+0.988 ± 0.166 (5.9σ)** | +0.539 / +0.295 |
| B | −0.183 ± 0.109 (1.7σ) | −0.202 ± 0.040 (5.1σ) | −0.047 / −0.072 |
| C | −0.146 ± 0.164 (0.9σ) | −0.195 ± 0.106 (1.8σ) | −0.075 / −0.079 |

### 1. The control reproduces the degradation

Arm A rises at 7.1σ / 5.9σ and ends **+0.539 / +0.295 worse than the
checkpoint it started from** — 4.0× its own mean adjacent swing. That is what
makes B and C interpretable: the arms differ in exactly one thing, so anything
they do better is attributable to the schedule.

Degradation from the peak is FASTER than the 1B chain's late leg (+1.691 vs
+0.753 STACK). That is consistent with the gate's retraction and sharpens it:
the slower late-leg number was partly the flattening effect of averaging over a
longer, later window.

### 2. Decay halts and slightly reverses it

Arms B and C both END BETTER THAN THE BRANCH on both held-out sets, where the
control ends 0.5 nats worse. Against the control at the same token count, B is
−0.586 / −0.367 and C is −0.614 / −0.375.

**All five acceptance criteria pass for both B and C:** no significant positive
slope on either set (both are negative), endpoint no worse than the branch
(both better), numerically stable (zero NaN/Inf, zero interruptions, zero
replayed microsteps in all three arms), and the winner is consistent across
both held-out domains at every point.

### 3. It is the SHAPE, not the magnitude — halving the LR bought nothing

This is the separation the campaign was designed to make.

    C - B endpoint:  STACK -0.028   WEB -0.008
    mean adjacent swing (B): STACK 0.027  WEB 0.018

C's advantage over B is **the size of the local noise** — about 1σ of the
point-to-point swing on STACK and well under it on WEB. B and C are
indistinguishable, and C's slopes are the more weakly resolved of the two
(0.9σ / 1.8σ versus B's 1.7σ / 5.1σ).

So: once the schedule decays, halving the peak LR adds nothing measurable.
**The fix is the decay, not a lower rate.** This retires the search for "the
correct held LR" that consumed three earlier attempts (3e-4 and 1e-4 at item
10, held 3e-5 on the first intermediate chain, 1.5e-5 at the 1B gate) — every
one of which was a production cosine truncated by a short run.

**Recommended: arm B's schedule.** Keep the branch LR and size `total_steps`
to the horizon actually being run. C is not better beyond noise, and it gives
up learning rate for nothing.

### 4. A held LR also makes the trajectory CHAOTIC

Mean adjacent-point swing, which nobody set out to measure:

| arm | STACK | WEB |
|---|---|---|
| A (held) | 0.135 | 0.082 |
| B (decayed) | 0.027 | 0.018 |
| C (decayed) | 0.035 | 0.021 |

Decay reduces point-to-point noise **4-5×**. This bears directly on the 1B
gate's unexplained 0.272-nat chain-vs-arm discrepancy after a 600-microstep
replay: at a held rate the trajectory is genuinely unstable, so a small
perturbation moves held-out loss a lot. Under a decaying schedule it is
smooth. Any A/B at these sizes should decay, not because it converges better,
but because a held rate makes the measurement noisy enough to defeat itself.

## Method

The branch LR was reconstructed from the checkpoint's OWN `train_cfg` record
(`lr=0.000015, sp1=8192, sp2=5516582, sp3=0.0000045` at `step_count=64000`)
through the formula transcribed from `stdlib/nsl/optim/schedulers.nsl:21` —
never copied out of a comment. Arm B's `base_lr` is SOLVED so that its curve
passes through that value at the branch, which makes it a curve parameter
rather than a starting rate. C halves `base_lr` and `min_lr` together, which
halves the whole curve exactly, because `lr = min + (base-min)k` is linear in
`(base, min)` jointly — verified at every scored point (ratio 0.500000).

Verified before spending GPU time:
- **Arm A resumes with NO trajectory-drift acknowledgment**, while B refuses
  without one, naming both `lr` and `sp2`. A control that needs an override is
  not a control.
- Each arm's `train_cfg` was read back **out of the compiled binary** to
  confirm the LR reached codegen — the PR #520 inert-clause class.
- `gen_arms.py` asserts its own diff: 1 changed line for A, 3 for B and C, each
  of which must be the optimizer, scheduler or checkpoint line. It refuses to
  rewrite the control at all, because `train_cfg` is a STRING and re-rendering
  `0.000015` as `1.5e-05` is textually different while numerically identical.
- cuBLASLt and the bf16 cast cache are OFF in all three arms. All three share
  ONE execution fingerprint.

Every point carries an Experiment Lineage Record (`campaign-sched3/lineage.py`)
read from the artefacts themselves. `score_arms.py` ingests records rather than
filenames and REFUSES a series that mixes arms, has unequal interval widths,
disagrees between filename and record, changes fingerprint mid-arm, or whose
theta bytes no longer match. Each refusal was demonstrated against a synthetic
series before the tool was trusted — which is how a dead guard was found: the
original duplicate-step check was unreachable, because filenames encode the
step. It was replaced with a filename↔record agreement check, which catches the
actual failure mode (a file named `m88000` whose record says `80000`).

The branch re-scored **bit-identically** to the 1B campaign's recorded value
(3.872422343150514 / 5.834139979276501) on a binary including #541/#546/#551,
so this comparison is toolchain-invariant and the 262M peak is independently
reconfirmed.

## Caveat

B and C end AT `min_lr`, so their final points are at a near-frozen rate, and
"no significant positive slope" is easy to pass by barely moving. That is why
criterion 3 carries the weight here: both arms end BETTER than the branch, and
B's WEB declines monotonically across all four points, so they are improving
rather than merely stopping.

One scored point (B at micro 80,000) aborted transiently inside
`nsl_tensor_to_device` and was re-scored successfully. The scorer prints
`FAILED` and names its stderr rather than `0.0000`; in this campaign a
`0.0000` would have entered the table as the best result in the run.
