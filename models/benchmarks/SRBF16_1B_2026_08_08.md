# SR-BF16 at 1B@2048: streaming is gone, and it bought nothing

RTX PRO 4500 Blackwell, 32,623 MiB installed / **32,143 MiB reported by
`cuMemGetInfo`** (the figure the capacity arithmetic below uses), CUDA 13.x.
Timing from `matrix_bench.py`, 3 rounds, timing pass uninstrumented. Memory
from `residency_probe.py` (new — see "Why a second instrument" below).

> **Read the throughput numbers with this caveat.** `matrix_bench` interleaves
> the arms *within one invocation*, and that is what makes its comparisons
> sound. Restricting a run with `--arms` to a single arm degenerates that to
> three repeats of one arm, and each arm here was run in its own process
> (12:04, 12:10 and 12:43) precisely so its microbatch probe would find its
> OWN ceiling. So the sub-1% throughput deltas in §2 and §6 are
> **cross-process, not interleaved** — the harness's own docstring says that
> is the confound it exists to remove, and PR #454's phantom "40% win" is why.
> Treat every throughput delta under a few percent in this document as
> "indistinguishable", not as a measurement. The **capacity** results are
> unaffected: OOM / no-OOM does not depend on clocks.

The question this answers: *does bf16-sr's resident BF16 storage eliminate
enough streaming at the real long-sequence configuration without producing
another capacity bottleneck?*

**Streaming: eliminated, completely — 0.5 MiB/step against the streaming
baseline's 3,712 MiB/step. Capacity: yes, there is another bottleneck, and
bf16-sr cannot reach it.** At the peak that decides whether the
configuration fits, the parameters bf16-sr halves are **11% of the
footprint**. Activations are 51% and f32 optimizer moments are 39%. The
microbatch ceiling at seq 2048 is **1**, and it is 1 for f32 too.

**And then the bottleneck moved.** The microbatch-2 OOM turns out to be the
materialized CE logits tensor, and the belief that the fused LM head could
not be used here was a stale comment. Turning it on —
`--fuse-lm-head require` composed with `--layerwise-accum` and
`--param-dtype bf16-sr`, all three live together — **runs at microbatch 2**,
where both arms measured there OOM (§6). So the answer to "is there another
capacity bottleneck" is yes, it is activations, and it is addressable.

## 1. Streaming

| arm | flags beyond `--source-ad` | PCIe H2D **per step** |
|---|---|---|
| `layerwise` | `--checkpoint-blocks --layerwise-accum --weight-stream`, `NSL_WS_RESIDENT=0` | **3,712 MiB** † |
| `layerwise_policy` | same flags, residency policy ON | **0.5 MiB** |
| `layerwise_resident_srbf16` | `… --weight-stream --param-dtype bf16-sr` | **0.5 MiB** |

† Carried from the 2026-08-08 residency campaign
([RESIDENCY_1B_2026_08_08.md](RESIDENCY_1B_2026_08_08.md)), where it was read
off the weight-stream counter as the whole 144-parameter surface re-uploaded
every step. It was **not** re-measured here; the two 0.5 MiB figures were.

bf16-sr moves no parameter bytes across PCIe at 1B. Confirmed three ways:
the attribution pass's per-step counter (0.5 MiB, which is the DataLoader's
batch), the teardown counters, and the weight-stream table being *empty* —

```
[sr-bf16] teardown: 144 bf16-authoritative param(s), 4176 SR optimizer step(s),
          12672 widen-upload(s), 464 batched launch(es)
[weight-stream] uploads: 0 evicts: 0 writeback: 0 registered: 0 ptr_moves: 0
```

`registered: 0` is the structural point: `nsl_weight_stream_register`
redirects to `srbf16_register` before the capacity policy is consulted
(`weight_stream.rs:289`), so under bf16-sr the residency policy shipped
in #500 never runs at all. The 12,672 widen-uploads are device-to-device casts
from the bf16 mirror, not host transfers.

**But this is no longer a differentiator.** `layerwise_policy` — plain f32,
same flags — also moves 0.5 MiB/step, because #500 already pins all 144
parameters on this card:

```
[weight-stream] residency: pinned=144 of 144 param(s) pinned_mib=3712.2
   streamed_mib=0.0 free_at_decision=18595 MiB total=32143 MiB
   reserve=16072 MiB must_free=0 MiB
```

Both routes reach zero streaming. bf16-sr gets there by never having a host
mirror; f32 gets there by deciding it does not need one.

## 2. Throughput: a dead heat

| arm | rounds (ms/step) | best | tokens/s | MFU% (tf32) |
|---|---|---|---|---|
| `layerwise_policy` (f32 resident) | 792.9 / 787.4 / **771.5** | 771.5 | **2,654.6** | 20.7 |
| `layerwise_resident_srbf16` | 790.6 / 817.2 / **772.2** | 772.2 | **2,652.1** | 20.7 |

**0.09% apart** — well inside round-to-round spread (the srbf16 arm's own
rounds span 5.8%), and cross-process besides. These two are indistinguishable.

Both MFU figures are against the **tf32** roofline (87.6 TFLOPS), including
the bf16-sr arm. `--param-dtype bf16-sr` is a *storage* dtype: the mirror is
widened to an f32 working view before the GEMM and these arms set no matmul
env, so the GEMM runs TF32 — the run log says so verbatim
(`[nsl-matmul] cuBLAS math mode: TF32 tensor cores`). The harness had been
quoting the srbf16 arms against the 200.3 TFLOPS **bf16** peak, understating
their MFU by 2.29x (this cell read 9.1%). Fixed in this commit; it also
corrects the 500M `srbf16` row in MATRIX_2026_08_06, which has the same bug.

The 2026-08-08 campaign read bf16-sr as ~1% slower once residency is
equalised. This run cannot resolve 1%, so it neither confirms nor refutes
that; what it does establish is that the two are within noise of each other
against a policy-ON f32 baseline rather than a flag-absent one.

## 3. Capacity: the ceiling is 1, for both

Each arm was probed **alone**, so the ceiling is its own. This matters:
`largest_fitting` returns the largest microbatch that fits *every arm in the
cell*, and the full 1b@2048 cell contains `reference` and `optimized`, which
OOM at microbatch 1 — so the "microbatch 1" in every previous 1B matrix was
a fallback, not a measured srbf16 ceiling. It had never been measured.

```
srbf16:            batch 16 OOM · 8 OOM · 4 OOM · 2 OOM · 1 ok
f32 (policy on):   batch 16 OOM · 8 OOM · 4 OOM · 2 OOM · 1 ok
```

**Halving the weight surface does not buy a microbatch.**

## 4. Where the memory actually is

Composition **at the global allocated peak** — the instant that decides
whether the configuration fits — at microbatch 1:

| surface | f32 resident | srbf16 | delta |
|---|---|---|---|
| activations | 10.42 GB | 10.41 GB | — |
| `optim_m` + `optim_v` (f32) | 8.00 GB | 8.00 GB | — |
| weights | 4.02 GB | **2.20 GB** | **−1.81 GB** |
| **peak allocated** | **22.43 GB** | **20.62 GB** | **−1.81 GB** |

Activations agree to 10 MB across the two arms, which is the cross-check
that the split is real: the arms differ *only* in parameter dtype, so
anything else moving would have meant the accounting was wrong (it was —
see §6).

bf16-sr saves exactly what it claims, 1.81 GB, half of the 3.62 GiB
occupied by the 144 layer parameters. The remaining 400 MB of `weights` is
the f32 embedding, which is not in the registered set and stays f32.

**And that saving is 17% of one microbatch.** Activations cost ~10.4 GB per
microbatch at seq 2048. Going from 1 to 2 needs another ~10.4 GB; bf16-sr
supplies 1.81 GB of it. That is the whole answer to the capacity question —
the ladder rung is six times taller than the saving.

The microbatch-2 OOMs confirm it directly, both arms dying at essentially
the same place on a 32,143 MiB card. These are the surfaces **at the instant
the process aborted**, so each is a LOWER BOUND on what that configuration
wanted, not its peak demand:

| at the OOM (microbatch 2) | f32 resident | srbf16 |
|---|---|---|
| activations | 17.48 GB | 19.26 GB |
| `optim_m` + `optim_v` | 8.00 GB | 8.00 GB |
| weights | 4.02 GB | 2.43 GB |
| nvidia-smi peak (this PID) | 30,770 MB | 30,806 MB |

### The failing allocation names itself

srbf16, microbatch 2:

```text
[nsl] GPU out of memory
Requested:    805306368 (768.0 MB)
VRAM free:    316.6 MB / 31.39 GB
Pool drained: 168.0 MB
  Operation: matmul_f32
```

`805,306,368 = 2 × 2048 × 49152 × 4` — batch × seq × vocab × f32. **The
allocation that fails is the materialized CE logits tensor**, the exact
surface the fused LM head exists to remove. The card is not merely full; it
is full *and* the next request is the one the fusion would delete. §6 turns
that observation into an experiment.

The OOM's context table breaks the activation surface down by producing op:

```text
matmul_f32          6.50 GB (113 blocks)
nsl_add_f32         4.26 GB (178 blocks)
nsl_mul_f32         3.25 GB  (84 blocks)
nsl_silu_f32        2.00 GB  (16 blocks)
dropout_f32         1.50 GB  (48 blocks)
rmsnorm_f32         1.06 GB  (34 blocks)
nsl_rotate_half_f32 640.0 MB (32 blocks)
```

So it is not one tensor: the elementwise chain (`add`/`mul`/`silu`/
`dropout`/`rmsnorm`/`rotate_half`) accounts for **12.7 GB**, more than the
matmul outputs. `--checkpoint-blocks` is on; these survive it because the
CSLA window backward holds each micro-batch's boundary residuals.

## 5. What this means for the production path

The levers, in order of what they are worth at 1B@2048:

1. **Activations — 10.4 GB per microbatch, 51% of the peak.** The fused LM
   head is **off** in both arms (`fused_lm_head: False`), so the CE logits
   chain is materialized at `batch × 2048 × 49152` f32 — and the microbatch-2
   OOM is that exact tensor. This is the only surface big enough to change
   the ceiling.

   **It is off because these arms do not ask for it, not because it is
   refused.** `models/coder1b/pretrain_layerwise_fit.nsl`'s header says
   `@fused_lm_ce` "is refused under `--layerwise-accum` until its cast cache
   is tape-carried"; that is **stale**. `csla_layerwise_gate` asserts
   `[csla] fused-ce tape-carry: 1 slots` on `--layerwise-accum` arms today,
   and there is no refusal rule pairing the two in `feature_rules.rs`. These
   benchmark arms print `fused-ce tape-carry: 0 slots` because neither
   `--fuse-lm-head` nor `--pretrain-optimized` is among their flags. See §6 —
   this is measurable, and was measured.
2. **f32 optimizer moments — 8.00 GB, 39% of the peak.** Unchanged by
   bf16-sr *by construction*: `--param-dtype bf16-sr` refuses
   `--wggo-moment-precision` and CPDT reduced-precision moment plans
   (`feature_rules.rs:344`, `:369`). So the composition that would attack
   the second-largest surface is exactly the one bf16-sr forbids.
3. **Weights — 11% of the peak, and bf16-sr already halved them.** There is
   roughly 2.2 GB left here in total, most of it already spent.

bf16-sr's remaining value at 1B on this card is **1.81 GB of headroom at
equal throughput and zero PCIe** — real, but it is not a throughput win, not
a streaming win over what #500 already does, and not enough to move the
microbatch ceiling.

## 6. Following the evidence: the fused LM head moves the ceiling

§5 named the CE logits chain as the only surface big enough to matter, and
§4 showed the microbatch-2 OOM *is* that tensor. The stale-refusal claim was
the only thing standing between that observation and a test, so it was
tested. New arm `layerwise_srbf16_fusedce` = the srbf16 arm plus
`--fuse-lm-head require`.

`require`, not `auto`, deliberately: `auto` falls back to the composite path
with a note on stderr, which would have measured the unfused arm again under
a fused name. It compiled, and the fusion is witnessed in the build log —

```text
[lm-head-fusion] inferred: vocab=49152 hidden=2048 rows=1x2048=2048
                 bias=false (no @fused_lm_ce decorator needed; --fuse-lm-head require)
[csla] fused-ce tape-carry: 1 slots
```

`1 slots`, where every other arm in this document reads `0 slots`. So the
composition `--layerwise-accum` × `--param-dtype bf16-sr` × fused LM head is
legal and live today.

| at global peak | srbf16 mb 1 | **+fused mb 1** | **+fused mb 2** |
|---|---|---|---|
| activations | 10.41 GB | **9.27 GB** | 18.51 GB |
| `optim_m` + `optim_v` | 8.00 GB | 8.00 GB | 8.00 GB |
| weights | 2.20 GB | 2.43 GB | 2.43 GB |
| **peak allocated** | 20.62 GB | **19.70 GB** | **28.94 GB** |
| nvidia-smi peak | 23,596 MB | 23,212 MB | 30,992 MB |
| result | ok | ok | **ok — no OOM** |

**Microbatch 2 runs**, where both arms tested at microbatch 2 —
`layerwise_resident_srbf16` and `layerwise_policy` — OOM. (`layerwise`,
`layerwise_resident`, `reference` and `optimized` were not run at microbatch
2 in this campaign, so "every unfused arm" would be an extrapolation.)

The measured saving is **1.14 GB of activations at microbatch 1**, which is
the logits chain: the 402 MB logits tensor plus its softmax and gradient. At
microbatch 2 the two are not directly comparable — the unfused arm's
18.51-vs-19.26 GB gap is measured against a number truncated by its own
abort — so the honest statement is that the fusion frees enough to bring a
28.94 GB peak under a 31.39 GB card, not a specific microbatch-2 delta.

`matrix_bench`'s own probe reaches the same ceiling independently —
`16 OOM · 8 OOM · 4 OOM · 2 ok` — and times it there:

| arm | microbatch | rounds (ms/step) | best | tokens/s | tokens per optimizer step |
|---|---|---|---|---|---|
| `layerwise_policy` (f32) | 1 | 792.9 / 787.4 / **771.5** | 771.5 | 2,654.6 | 4,096 |
| `layerwise_resident_srbf16` | 1 | 790.6 / 817.2 / **772.2** | 772.2 | 2,652.1 | 4,096 |
| **`layerwise_srbf16_fusedce`** | **2** | 1531.0 / **1519.5** / 1526.5 | 1519.5 | **2,695.6** | **8,192** |

Runtime attribution agrees the fusion is live: `fused_lm_head: True`, against
`False` for both other arms. PCIe stays at 0.6 MiB/step.

**Throughput per token is flat; the win is capacity.** At
`grad_accumulation=2` the optimizer now sees 8,192 tokens per step instead of
4,096, on the same card, at the same tokens/s.

*Caveat on that +1.6%:* on top of being cross-process (see the note at the
top), the fused arm was measured while another session held this box at load
~7, whereas the two microbatch-1 arms ran on an idle machine (~0.7). That
biases the fused arm pessimistically, so "not slower" is safe; +1.6% is not
a measurement.

*On the capacity result being one lucky run:* it is not one run. Microbatch 2
completed **five separate times** — the `residency_probe` run, `matrix_bench`'s
3-step probe, and three 20-step timing rounds — across two processes. What it
is NOT is a wide margin: peak allocated 28.94 GB and peak reserved 29.95 GB
against 31.39 GB usable, so roughly 1.4 GB of headroom. The threat to that is
another process holding **VRAM**, not CPU load; this box runs a compositor and
concurrent sessions, so treat microbatch 2 as "fits on an otherwise-idle
card", not as a guarantee.

It trains: loss 11.20 → 7.88 over 29 micro-batches at microbatch 2 —
**14 optimizer steps**, not 29; the run prints one loss per micro-batch and
`grad_accumulation` is 2, which the teardown line confirms
(`2016 SR optimizer step(s)` ÷ 144 params = 14). No convergence claim is
made against the microbatch-1 arms: on the same 120,000-token budget they
take 29 optimizer steps to this arm's 14, so the loss values are not
comparable and this is only a sanity check that it trains at all.

This does not contradict §3–§5; it confirms them. bf16-sr's 1.81 GB was
never going to buy a microbatch because it is 17% of one. The fused LM head
attacks the surface that is 51% of the peak, and *that* is what moved the
ceiling. **The ordering in §5 was the right ordering, and lever 1 works.**

## 7. Two instrumentation defects this campaign had to fix first

Neither is a behaviour bug; both made the measurement unreadable, and the
first made bf16-sr look actively harmful.

**(a) bf16-sr's parameter surface was not accounted as `weights`.**
`alloc_managed` inherits whatever surface tag is ambient and `sr_bf16.rs` set
none of its own, so both halves of the parameter surface landed in the wrong
bucket — but in *different* wrong buckets, which is why the pre-fix table
looks strange rather than simply wrong:

| pre-fix, 1B@2048 mb 1 | bucket | bytes |
|---|---|---|
| bf16 authoritative mirrors (`srbf16_register`) | `activations` | 1.81 GB |
| widened f32 working views (`srbf16_upload`) | `other` | 3.63 GB |
| what `weights` was left holding | `weights` | 400 MB |

The register belt runs inside the step body where codegen has set
`activations`; the upload path runs where nothing has, so it fell through to
the default `other`. Net effect on the report: `weights 400 MB /
activations 12.23 GB`, i.e. bf16-sr appeared to make activations **1.81 GB
worse** while "saving" 3.62 GB of weights.

Both sites now tag `weights` via the pre-existing `SurfaceGuard`. **The fix
is pure accounting**, and the proof is that `Peak allocated` reads 20.62 GB
before and after on the same binary — the tag feeds counters only, never
pool selection. Post-fix, `other` is 0 B and activations land at 10.41 GB
against the f32 arm's 10.42 GB.

Pinned by a new gate, `srbf16_parameter_surface_is_accounted_as_weights_gpu`,
which was **verified to fail with the fix reverted** (`other` 132,096 B vs
`weights` 16,896 B). It asserts on the surface table's `current` column, not
`peak`: `weights` peak includes the correctly-tagged initial f32 allocation
in both states, so a peak-based assertion passes either way — the first
version of this gate did exactly that and was vacuous.

**(b) `matrix_bench`'s memory columns are not peaks.** `[gpu-mem]` prints
once per step, *after* the step's transients are released, so
`peak_alloc_mb` / `peak_driver_mb` describe the persistent surface between
steps. At this cell they report **12,304 MB** where the allocator's own
high-water mark is **20.62 GB** and nvidia-smi sees **23.6 GB** — a factor
of 1.9 against nvidia-smi (1.68 against the allocator's own high-water), and
the reason "12.3 GB on a 32 GB card" coexisted with an OOM at microbatch 2. Both columns now carry that caveat in the harness docstring.
No capacity conclusion should be drawn from them.

## Why a second instrument

`residency_probe.py` (new) exists because `matrix_bench.py` structurally
cannot answer capacity questions:

* it **kills** each run after `--max-steps`, so the `atexit` reporters — the
  weight-stream counters, the residency posture, the `NSL_MEMSTATS`
  high-water summary — never fire. The probe runs a short token stream to
  completion instead;
* its microbatch probe returns the largest batch fitting *every* arm in the
  cell, which is not any single arm's ceiling;
* it discards run stderr, which is where the per-surface attribution and the
  OOM diagnostic live. **An OOM is a result here, not a failed run** — it is
  the most informative output a failing arm produces.

`matrix_bench.py` also gained `--arms`, which restricts a cell so the
microbatch probe reports a ceiling for the arms you care about.

## Reproduce

```bash
# timing + per-arm microbatch ceiling
# --out per arm: both invocations otherwise write the same
# target/matrix_logs/matrix_results.json and the second wipes the first.
python3 models/benchmarks/matrix_bench.py --cells 1b@2048 \
    --arms layerwise_resident_srbf16 --rounds 3 --out target/srbf16_logs
python3 models/benchmarks/matrix_bench.py --cells 1b@2048 \
    --arms layerwise_policy --rounds 3 --out target/f32policy_logs
python3 models/benchmarks/matrix_bench.py --cells 1b@2048 \
    --arms layerwise_srbf16_fusedce --rounds 3 --out target/fusedce_logs

# true peaks, per-surface attribution, and the OOM one rung above the ceiling
python3 models/benchmarks/residency_probe.py --scale 1b --seq 2048 \
    --arm layerwise_resident_srbf16:1 --arm layerwise_policy:1 \
    --arm layerwise_resident_srbf16:2 --arm layerwise_policy:2
```

Raw data: `target/{srbf16,f32policy,fusedce}_logs/matrix_results.json`, and
per-arm `run_stderr.txt` + `probe_result.json` under `target/residency_probe/`.

Two caveats on the artifacts backing this document. The **nvidia-smi peaks
are sampled by the probe process**, so they appear in no run's stderr —
`probe_result.json` was added in this commit to persist them, which means the
figures quoted above were read from console output rather than from a file a
reader can open. Re-running the reproduce block regenerates them properly.
And the pre-fix surface tables (the `weights 400 MB / activations 12.23 GB`
readings in §7) come from `target/residency_probe/probe_console.txt`, a
capture taken before the accounting fix — deliberately kept, since it is the
evidence for the defect, but do not read it as current.

## Secondary observation

Both arms perform **144 `.item()` device-scalar reads per step, one per
parameter**, each forcing a full `cuCtxSynchronize()` (`tensor/mod.rs:1047`).
Identical count in f32 and bf16-sr, so this belongs to the CSLA schedule, not
to bf16-sr. The attribution pass charges it 88–95 ms of a ~780 ms step, but
that timer wraps the drain, so most of it is waiting for work already
queued — it bounds the **serialization**, not the overhead. Not investigated
further here.
